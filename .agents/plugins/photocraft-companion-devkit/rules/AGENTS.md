# PhotoCraft Companion DevKit — Генеральный регламент разработки

Данный свод правил является абсолютным законом для всех агентов и субагентов, работающих с кодовой базой **PhotoCraft Plugins & Companion**.

---

## 1. Ограничение ресурсов при компиляции (Resource Guard)
* **СТРОГО ЗАПРЕЩЕНО** запускать `cargo build`, `cargo check`, `cargo test`, `cargo clippy` без явного флага ограничения потоков:
  ```powershell
  cargo test --workspace -j 1
  cargo build --package companion_app --release -j 1
  ```
* Максимально допустимое значение: `-j 2` только при прямом согласовании с пользователем.
* В профилях `.cargo/config.toml` и `Cargo.toml` зафиксированы `jobs = 1` и `codegen-units = 1`. Никогда не перегружать CPU и RAM машины пользователя!

---

## 2. Критерий завершения задач (Definition of Done — 100% Тесты и Документация)
**КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** объявлять этап, задачу или исправление дефекта завершенным без выполнения двух обязательных условий в рамках одной итерации:

1. **100% успешный прогон форматирования и тестов воркспейса:**
   * Проверка стиля кода: `cargo fmt --all -- --check` обязана завершиться с кодом 0 и нулевым числом расхождений.
   * Команда `cargo test --workspace -j 1` обязана завершиться с кодом 0 и нулевым числом упавших тестов.
   * Проверка архитектурной чистоты: `cargo test -p ai_engine --test architecture_integrity_test -j 1` (нулевая толерантность к keyword-sniffing и хардкоду моделей).
   * Проверка соблюдения регламентов разработки: `cargo test -p ai_engine --test dev_regulations_lint_test -j 1` (синхронизация версий в 5 файлах, изоляция крейтов, Resource Guard, отсутствие дрифта каталога в README.md/README.ru.md, синхронность глав летописи RU/EN и запрет весов моделей в Git).
   * Обязательное прохождение `crates/overlay_ui/tests/i18n_lint_test.rs`:
     - Файлы `icons.rs`, `store.rs`, `theme.rs`, `toolstrip.rs`, `updater.rs`, `win32_window.rs` на 100% свободны от кириллицы (`\u{0400}..\u{04FF}`);
     - В `manager.rs` и `offline_modal.rs` любая кириллица строго обернута в `.t("En", "Ru")`;
     - Все пары переводов валидны, не пусты и не содержат плейсхолдеров (`TODO`, `FIXME`, `???`, `untranslated`).
   * Валидация каталога плагинов: `cargo run --package plugin_validator -j 1 -- --validate plugins`.

2. **Синхронное обновление документации проекта:**
   * **`docs/CHECKLIST.md`**: отметить выполненные пункты `[x]`;
   * **`docs/BUGS_AND_ISSUES.md`**: зарегистрировать дефект с кодом `BUG-XXX` или перевести в статус `RESOLVED` с описанием первопричины и решения;
   * **`docs/CHRONICLE.md` и `docs/CHRONICLE.en.md`**: синхронно добавить запись на русском и английском языках с точной отметкой времени в авторском стиле (*Время: ДД месяца ГГГГ, ЧЧ:ММ (~ХХ минут)*).

## 3. Железный запрет хардкода и keyword-sniffing (Zero-Core Hardcoding Prohibition)
* **СТРОГО ЗАПРЕЩЕНО** модифицировать исходный код ядра (`crates/companion_app`, `crates/ai_engine`, `crates/photocraft_bridge`) под логику конкретных плагинов:
  - Дописывать специальные `match`/`if` под ID плагинов;
  - Заниматься keyword-sniffing имен файлов или плагинов через `.contains("depth")`, `.contains("normal")`, `.contains("birefnet")`, `.starts_with()`, `.ends_with()`;
  - Хардкодить имена файлов моделей (`.onnx`, `.bin`, `.safetensors`) в кодовой базе ядра;
  - Подделывать манифесты (`required: false` для моделей `NativeAi`) ради фиктивного прохождения тестов;
  - Вшивать `image.revealAll`, `layer.mergeDown` и специфичные шаги внутрь Rust-кода.
* **МАРШРУТИЗАЦИЯ МОДЕЛЕЙ:** Любая маршрутизация моделей идет исключительно через поле `role` в DTO контрактов `core_contracts` (`manifest.model_by_role(...)`).
* **ГЛАВНЫЙ ЗАКОН:** Любой сторонний разработчик должен иметь возможность создать плагин (папка с `.onnx` и декларативным манифестом `plugin.json` или пакет `.pcpl`) — и он **ОБЯЗАН РАБОТАТЬ СРАЗУ, БЕЗ ИЗМЕНЕНИЯ КОДА ПРОГРАММЫ И БЕЗ ЕЁ ПЕРЕСБОРКИ**.
* Вся логика пайплайна плагина (входные данные, задача ИИ, пред- и пост-команды `commands` / `post_commands`, способ наложения результата) задается **ИСКЛЮЧИТЕЛЬНО ДЕКЛАРАТИВНО В `plugin.json`**.
* Ядро компаньона — исключительно нейтральный универсальный рантайм.

### 3.1. Обязательное условие: Наличие и формат README.md у каждого плагина (Mandatory Plugin README)
* **СТРОГО ОБЯЗАТЕЛЬНО:** Любая директория плагина в `plugins/<id>/` обязана содержать файл `README.md`.
* Создание, обновление или публикация плагина без оформленного `README.md` является **грубым нарушением Definition of Done (DoD)**.
* **Обязательная структура `plugins/<id>/README.md`:**
  1. **Заголовок и бейджи:** Название плагина, тип плагина (No-Code / Native AI), модель.
  2. **Двуязычное описание:** Синхронные разделы **English** и **Русский** с четким описанием назначения и того, что делает плагин.
  3. **Практические сценарии использования (Use Cases / Практическое применение):**
     - Минимум 2–3 конкретных примера реального использования в связке с инструментами PhotoCraft (какие слои выбирать, с какими фильтрами/режимами наложения комбинировать, какую пользу дает художнику или фотографу).
  4. **Ссылки на веса:** Если плагин использует нейросеть — прямые ссылки на Hugging Face / GitHub Releases.

## 4. Регламент изменения ядра программы под новые плагины
* **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО менять ядро программы под новый плагин втихаря!**
* Если для нового плагина недостаточно текущих возможностей манифеста `plugin.json`:
  1. Агент немедленно останавливает реализацию и выносит вопрос на обсуждение с автором / разработчиком.
  2. Агент формулирует, чего именно не хватает в контракте `core_contracts` (новый тип входа, новый метод IPC, новый параметр наложения).
  3. Изменение проектируется **только как общее декларативное расширение спецификации**, приносящее пользу всей экосистеме, а не как костыль под один частный случай.
  4. Правки в ядро вносятся только после явного утверждения автором.

## 5. Принцип технической честности (Zero-Yesman: аргументированная критика)
* **Агент обязан критически оценивать идеи автора, а не слепо поддакивать и внедрять заведомо провальные решения.**
* Если идея несет архитектурные риски, снижает безопасность или нереализуема в текущем стеке:
  1. **Исследование в сети:** Сначала агент обязан изучить вопрос (issue трекеры библиотек `ort`, `winit`, `egui`, стандарты ОС, бенчмарки).
  2. **Прямое и честное предупреждение:** Открыто изложить риски разработчику:
     > *«Данная идея несет следующие критические риски: [1, 2, 3]. В таких-то условиях это приведет к [панике в egui / зависанию UI-потока / отказу в Win32 / утечке памяти]. Вот почему отраслевой стандарт решает задачу иначе. Предлагаю альтернативный вариант: [...]»*.
  3. Реализация начинается только после взвешенного выбора оптимального пути.

## 6. Запрет невоспроизводимых символов в интерфейсе (Vector-First UI)
В базовом шрифте `egui` нет расширенных Noto/Emoji шрифтов. При попытке вывода неподдерживаемых глифов интерфейс ломается уродливыми квадратами «тофу» (`□`) (история дефектов BUG-005, BUG-012, BUG-021, BUG-033).

* **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ любые Emoji в текстовых строках UI:**
  ❌ `⏳`, `⚠️`, `⬇`, `⬆`, `⬅`, `➡`, `✨`, `🪄`, `🔥`, `🚀`, `💡`.
* **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ спец-символы Unicode:**
  ❌ `●` (U+25CF), `•` (U+2022), `✓`, `✔`, `✕`, `✖`, `⚙`, `🔍`.
* **ЖЕЛЕЗНЫЕ ПРАВИЛА ОТРИСОВКИ:**
  1. **Индикаторы статуса, точки подключения и бейджи:** **СТРОГО** отрисовывать векторным кружком через `ui.painter().circle_filled(center, radius, color)`.
  2. **Служебные иконки (шестеренка, стрелки ориентации, полосы захвата, крестики):** отрисовывать векторными примитивами `line_segment(...)`, `circle_stroke(...)`, `rect_stroke(...)` или векторными SVG через `SvgIconCache`.
  3. **Индикатор занятости (Busy):** в текстовых кнопках использовать `"..."` с активной векторной рамкой свечения; в модальных окнах — векторный пульсирующий круг.

## 7. Подготовка авторелизов без ошибок в Git-репозитории

### А. Релиз плагинов (`publish_plugins.yml`):
* Перед пушем изменений в `plugins/**` **ОБЯЗАТЕЛЬНО** запустить локально:
  ```powershell
  cargo run --package plugin_validator -j 1 -- --validate plugins --build-registry --package-plugins --update-readme README.md --update-readme README.ru.md
  ```
* Если таблицы каталога в `README.md` и `README.ru.md` изменились, их **ОБЯЗАТЕЛЬНО закоммитить вместе с плагином**.
* *Почему это важно:* Если запушить без обновленного README, GitHub Actions сгенерирует автокоммит на сервере, локальная ветка отстанет от `main`, и следующий локальный пуш упадет с ошибкой `rejected (non-fast-forward)`.
* Веса моделей `.onnx` никогда не коммитятся в Git (строго в `.gitignore`).

### Б. Релиз приложения (`release.yml`):
* Версия приложения обязана быть синхронизирована байт-в-байт в 4 файлах:
  1. `Cargo.toml` (`[workspace.package] version = "X.Y.Z"`);
  2. `scripts/package_release.ps1` (`$Version = "X.Y.Z"`);
  3. `scripts/package_release.sh` (`VERSION="X.Y.Z"`);
  4. `packaging/windows/installer.iss` (`#define MyAppVersion "X.Y.Z"`).
* В коде не должно быть ни единого предупреждения компилятора (`RUSTFLAGS="-D warnings"`).

## 8. Проактивная оркестрация субагентов и параллелизм
Контекст главного агента быстро переполняется объемными логами сборки и кодовыми диффами нескольких крейтов.

* **ПРАВИЛО ОРКЕСТРАЦИИ:** Главный агент обязан **проактивно предлагать запуск специализированных субагентов**:
  - `bridge-specialist`: правки и тесты сокета 18492 и `core_contracts`;
  - `ai-specialist`: тензоры, ONNX Runtime, DirectML/CPU fallback;
  - `ui-specialist`: egui/eframe, оверлей, темы, векторный UI;
  - `chronicle-writer`: двуязычная авторская хроника в `docs/CHRONICLE.md`;
  - `quality-auditor`: прогон тестов с `-j 1`, линтер локализации и проверка DoD.
* **ПАРАЛЛЕЛЬНЫЙ ЗАПУСК:** Если задачи независимы (например, параллельная реализация UI и обновление летописи, или одновременная работа над двумя плагинами), главный агент запускает субагентов **параллельно** в одном вызове `invoke_subagent`.
* **ЧИСТЫЙ КОНТЕКСТ:** Главный агент не затягивает в себя сотни строк вывода консоли. Он агрегирует отчеты субагентов, проверяет финальный результат и кратко докладывает пользователю.
* **АВТОМАТИЧЕСКАЯ ПЕРЕДАЧА РЕГЛАМЕНТА СУБАГЕНТАМ:** Главный агент **ОБЯЗАН АВТОМАТИЧЕСКИ** включать директиву обязательного соблюдения `SUBAGENT_GUARDRAILS.md` во все промпты субагентов при вызове `invoke_subagent`. Пользователю НЕ требуется напоминать об этом.

## 9. Шлюз главного агента (Запрет слепого доверия и личный аудит diff)
* **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО принимать отчёт от субагента без личной проверки `git diff`**:
  - Главный агент обязан лично просмотреть `git diff` и убедиться, что субагент не вшил костыли, keyword-sniffing (`.contains()`), прямые имена `.onnx` или манипуляции флагом `required: false`.
* **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО объявлять пользователю «всё готово» без верификации на реальных условиях**:
  - Нельзя ограничиваться синтетическими мини-квадратиками 16x16.
  - Обязательно проверять граничные случаи: отсутствие моделей на диске, откат на CPU, форматирование кода (`cargo fmt --all -- --check`).
* **ПРИНЦИП АРХИТЕКТУРНОЙ ЧИСТОТЫ:** Любое расширение возможностей плагинов проектируется исключительно как общее декларативное поле контрактов `core_contracts`, а не как частная заплатка под один плагин.
