# Генеральная инструкция для агентов (Master Operating Guide)

Данный документ является высшим нормативным регламентом для всех агентов, работающих над кодовой базой **PhotoCraft Plugins & Companion**.

---

## 1. Архитектура и зоны ответственности

Проект организован как модульный Cargo Workspace монорепозиторий:

* `crates/core_contracts/` — **Общий слой абстракций**. Трейты, протоколы, структуры данных DTO, типы ошибок (`Result<T, CompanionError>`), модели команд и контракты плагинов.
* `crates/photocraft_bridge/` — **Зона Агента 1 (Мост)**. Асинхронный клиент на `tokio` к сокету PhotoCraft (порт 18492), выполнение JSON-RPC методов (`engine.execute`, `doc.inspect`, буфер обмена).
* `crates/ai_engine/` — **Зона Агента 2 (ИИ-движок)**. Крейт `ort` (ONNX Runtime bindings) для запуска RMBG-1.4 с DirectML (Windows), CoreML (macOS) и CUDA/CPU (Linux/BSD).
* `crates/overlay_ui/` — **Зона Агента 3 (Интерфейс)**. Кроссплатформенная панель на `egui`/`eframe`, оформленная в едином стиле с PhotoCraft.
* `crates/companion_app/` — **Главное приложение**. Сборка dependency injection, системный трей (`tray-icon`), точка входа.
* `plugins/` — **Каталог действий**. Конфигурационные манифесты действий (например, `remove_bg`).
* `chronicle_writer` — **Агент-Летописец**. Ведение двуязычной летописи разработки в `docs/CHRONICLE.md` и `CHRONICLE.en.md`.

---

## 2. Железные правила разработки

1. **Изоляция пакетов:**
   * Никаких прямых перекрёстных зависимостей между `photocraft_bridge`, `ai_engine` и `overlay_ui`. Связь только через интерфейсы `core_contracts`.
2. **Бесшовность (In-Place Updates):**
   * Результат работы плагина должен применяться к холсту автоматически.
3. **Регистрация дефектов (`docs/BUGS_AND_ISSUES.md`):**
   * Каждый баг регистрируется с префиксом `BUG-XXX` и статусом `NEW` / `IN_PROGRESS` / `RESOLVED`.
4. **Синхронизация летописи:**
   * Каждая запись ведётся синхронно на русском (`CHRONICLE.md`) и английском (`CHRONICLE.en.md`) с указанием времени: `*Время: ДД месяца ГГГГ, ЧЧ:ММ (~ХХ минут)*`.
5. **Абсолютный запрет завершения без тестов, форматирования и документации (Definition of Done):**
   * **СТРОГО ЗАПРЕЩЕНО** считать любой этап, задачу, спринт или исправление дефекта завершенным без выполнения обязательных условий:
     * **1. Чистота форматирования кода (Rustfmt Guard):** Команда `cargo fmt --all -- --check` обязана завершаться с кодом 0 и нулевым числом стилевых расхождений.
     * **2. Полное прохождение тестов:** Команда `cargo test --workspace -j 1` обязана завершаться с кодом 0 и нулевым количеством упавших тестов. Все новые фичи должны сопровождаться модульными/интеграционными тестами, ядро — проверяться линтером архитектурной чистоты `cargo test -p ai_engine --test architecture_integrity_test -j 1`, соблюдение правил репозитория — линтером регламентов `cargo test -p ai_engine --test dev_regulations_lint_test -j 1`. Интерфейс обязан проверяться линтерами `i18n_lint_test` и `vector_first_lint_test`.
     * **3. Валидация каталога плагинов:** Команда `cargo run --package plugin_validator -j 1 -- --validate plugins` обязана проходить с 0 ошибок.
     * **4. Актуализация всей документации:** Все файлы документации проекта (`docs/CHECKLIST.md`, `docs/BUGS_AND_ISSUES.md`, `docs/CHRONICLE.md`, `docs/CHRONICLE.en.md`) должны быть обновлены в той же итерации, отражая точный реальный статус системы.
6. **ЖЕЛЕЗНОЕ ОГРАНИЧЕНИЕ РЕСУРСОВ ПК ПРИ КОМПИЛЯЦИИ (Resource Guard):**
   * **СТРОГО ЗАПРЕЩЕНО** запускать `cargo build`, `cargo check`, `cargo test` или `cargo clippy` без явного жесткого ограничения нагрузки на CPU и RAM.
   * Обязательно использовать флаг потоков `-j 1` (или максимум `-j 2`) и следить за `codegen-units=1` во избежание зависания системы пользователя и исчерпания памяти.
   * Любые сборки и проверки должны быть максимально щадящими к процессору и оперативной памяти рабочей станции.
7. **ЖЕЛЕЗНЫЙ ЗАПРЕТ ХАРДКОДА И KEYWORD-SNIFFING (Strict Zero-Core Hardcoding Prohibition):**
   * **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** модифицировать кодовую базу ядра компаньона (`crates/companion_app`, `crates/ai_engine`, `crates/photocraft_bridge`) под логику конкретных плагинов (дописывать специальные `match`/`if` под ID плагинов, проверять имена файлов или моделей через `.contains()`, `.ends_with()`, вшивать `image.revealAll`, `layer.mergeDown` и специфичные шаги внутрь Rust-кода).
   * **ГЛАВНАЯ ЦЕЛЬ АРХИТЕКТУРЫ:** Любой пользователь или сторонний разработчик должен иметь возможность создать плагин (папка с `.onnx` и декларативным манифестом `plugin.json` или пакет `.pcpl`), положить в `plugins/` — и плагин **ОБЯЗАН РАБОТАТЬ СРАЗУ, БЕЗ ИЗМЕНЕНИЯ КОДА ПРОГРАММЫ И БЕЗ ЕЁ ПЕРЕСБОРКИ**.
   * Вся логика рабочего процесса плагина (входные данные, задача ИИ, пред- и пост-команды `commands` / `post_commands`, режим вывода) задается **ИСКЛЮЧИТЕЛЬНО ДЕКЛАРАТИВНО В MANIFEST `plugin.json`**.
   * Ядро компаньона — это исключительно нейтральный универсальный рантайм, интерпретирующий декларативные манифесты.
8. **СТРОГИЙ ЗАПРЕТ ВЫЗОВА ВНЕШНЕГО MCP SHELLIT:**
   * **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** вызывать любые инструменты MCP-сервера `shellit`, если пользователь прямо и явно об этом не попросил. Литературный термин «стиль Shellit» относится исключительно к слогу летописи и не имеет отношения к MCP-инструменту. Субагенты передают результаты главному агенту через сообщения.
9. **ШЛЮЗ ГЛАВНОГО АГЕНТА (Запрет слепого доверия / Zero-Blind Trust Gateway):**
   * Главный агент **не имеет права принимать отчёт от субагента** без личной проверки `git diff` на предмет костылей, keyword-sniffing и хардкода.
   * Главный агент **не имеет права писать пользователю «всё готово»**, пока результат не проверен на реальных граничных условиях (а не на синтетическом квадратике 16x16).
   * При любых сомнениях главный агент обязан требовать от субагента приведения решения к строгому декларативному контракту через `core_contracts`.
